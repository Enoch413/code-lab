# 공개 정보·자격증명 노출 대응안

상태: 공개본 배포 전 준비안. 2026-10-21 승인된 G2에서 Pages 소스를 Actions로 전환하고 `github-pages` 환경에 main 제한·필수 승인자 Enoch413을 설정했다. G3 수동 workflow는 로컬 활성화·검토 단계이며 이번 G3 변경의 커밋·푸시·실행·배포는 하지 않았다. 운영 Auth·Firestore·Storage·공개 Git 이력·캐시 변경과 메일·지원 요청은 실행하지 않았다. 이 문서에는 실제 사용자 이름·Firebase 계정 ID·비밀번호·토큰을 적지 않는다.

## A. 긴급 공개본 정리

`node tools/build-public.mjs`는 검토된 P0 커밋 `ac4689d8bf8fa1d30b574c2e323bdccc085fca1c`에서 앱 파일 18개만 읽고 빈 정적 데이터 2개와 `.nojekyll`을 생성한다. `.local/public-release-*/site`의 21개 파일만 배포 후보이며, 옆의 `release-report.json`은 공개 대상이 아니다. 매번 새 디렉터리를 만들며 기존 산출물·원본을 삭제하거나 덮어쓰지 않는다.

이 기준 커밋의 Firestore 규칙은 기존 운영 보존본 `0631677`와 동일하다. 이후 P1/P2 기능·새 권한 계약은 긴급 산출물에 포함하지 않는다. 이는 현재 최신 앱 전체의 배포 승인이 아니다. 공유 PDF LAB, 새 규칙·인덱스·마이그레이션 배포는 별도 전환이다.

기존 `session.json`에는 비어 있지 않은 자료 비밀번호가 있어 원본을 무시된 보호 폴더에 보존한 후 추적 파일은 빈 자료로 바꿨다. `check_data.json`도 빈 자료로 바꿔 실제 반·자료를 공개 소스에서 분리했다. Firebase 운영 문서는 건드리지 않았다. 로컬 미리보기는 비공개 파일을 사용자가 선택해 불러오는 방식으로 사용할 수 있다. 비공개 원본을 웹 루트나 Git에 복사해서는 안 된다.

명단·CSV·운영 도구·README·인수인계/복원 문서·백업·규칙·환경 파일은 산출물에 포함하지 않는다. 현재 소스 전체를 복사하거나 저장소 루트를 업로드하면 이 제한이 무효가 된다. 검사는 추가 파일·비어 있지 않은 정적 자료·고확신 비밀 마커·로컬 참조 누락을 거부한다. 모든 개인정보나 모든 표현 방식의 비밀번호를 자동 인식하는 검사는 아니다. 최종 운영자 검토와 보존 원본에 대한 메모리 내 일치 검사를 함께 수행한다. 공개 Firebase 클라이언트 설정은 서비스 계정 비밀키와 구분한다.

공개 Git 소스 재유입 방지를 위해 추적된 모든 CSV는 확장자 대소문자와 경로에 관계없이 거부한다. 유일한 예외는 정확한 `tools/firebase_bulk_users_template.csv` 경로이며, 기존 헤더만 있어야 한다. 데이터 한 줄이 헤더를 대신한 경우와 데이터 행 추가도 거부한다. 검사 오류에는 CSV 내용을 출력하지 않는다.

### 별도 승인 후 적용할 순서

1. 변경 파일·산출물 해시·검사 결과·알려진 민감 값 일치 0건을 검토한다. G1에서 관측했던 main 루트 자동 배포 설정은 승인된 G2에서 변경했다. 이후 공개본 배포는 하지 않았다.
2. **어떤 push보다 먼저** G2 설정이 유지되는지 확인한다. 2026-10-21 G2 직후 API 재조회에서는 Actions 소스, `github-pages` 환경의 main 브랜치 제한과 필수 승인자 Enoch413을 확인했다. 자기 승인 방지는 기존 false를 유지했으므로 독립된 두 번째 승인자를 요구하는 설정은 아니다. 설정 드리프트가 있으면 중단하고 재검토한다.
3. `.github/workflows/pages-emergency.yml`에 수동 workflow를 로컬 준비했다. 보호된 원본·검토 로그·기존 산출물은 제외하고 공개 변경만 별도 승인 후 선별 커밋·push한다. workflow는 `workflow_dispatch`만 허용하고 build는 main에서만 실행하며, 배포는 build 성공과 `github-pages` 환경 승인이 필요하다. push 이벤트 자동 배포를 추가하지 않는다. 로컬 활성화만으로 GitHub에서 실행되지는 않는다.
4. 승인된 push 이후 수동 workflow로 고정 P0 소스를 빌드한다. 사이트 파일 경로만 upload-pages-artifact에 전달하고 환경 승인 후 deploy-pages로 적용한다. Firebase CLI·프로젝트 계정·규칙 배포 명령은 이 후보에 없다.
5. 배포된 앱·PWA 경로와 로그인 화면, CSV·백업·인수인계·환경/규칙 파일 경로의 404를 확인한다. 공개 파일 본문을 보고서에 복사하지 않고 상태·해시·검사 건수만 기록한다. 실제 로그인은 아래 별도 승인이 있을 때만 한다.
6. 실패하면 민감 정보가 있던 저장소 루트/구형 전체 배포로 복구하지 않는다. 노출 없는 정비 화면 또는 검증한 안전 산출물을 사용한다. 파일 제외로 과거 다운로드본·캐시·Git 이력이 철회됐다고 판단하지 않는다.

GitHub Pages는 빌드 소스를 Actions로 설정하고 별도 사이트 산출물을 업로드할 수 있다. [공식 Pages 설정](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [공식 사용자 workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## B. 계정·세션 대응 범위 — 실행하지 않음

이전 로컬/공개 점검에서 명단 32행과 서로 다른 초기 비밀번호 값 3개가 일치했다. 행 수를 현재 유효 계정 수로 해석하지 않는다. 기존 값으로 로그인해서 유효성을 시험하지 않는다.

- 승인 대상: 현재 Auth UID와 명단의 일치 확인, 변경할 계정 목록, 관리자 우선순위, 안전한 새 자격증명 전달 방법, 세션 폐기·검증 시간, 실패 시 중단 기준. 이름만 맞으면 실행하지 않는다. 이 UID별 목록은 비공개로만 보관한다.
- 확인된 노출 계정에 한해 개별 자격증명 변경/재설정과 refresh token 폐기를 계획한다. 모든 계정을 일괄 삭제·재생성하거나 공통 비밀번호를 배정하지 않는다. 관리자 접근 연속성을 먼저 확인한다.
- 재설정 메일 발송도 외부 메시지이므로 이번 범위에 포함하지 않는다. 새 비밀번호·재설정 링크·토큰을 터미널, CSV 내보내기, 이슈, Git, 보고서에 넣지 않는다.
- refresh token 폐기는 현재 발급된 ID token의 모든 요청을 즉시 거부한다는 보장이 아니다. ID token은 약 1시간 유효할 수 있고 서버의 폐기 확인·권한 차단 계약도 함께 검토해야 한다. 즉시 차단이 필요하면 승인된 계정의 Auth/프로필 비활성화 방식을 따로 검토하고 기존 권한 계약과 실제 동작을 검증한다. 이번 작업에서 새 차단 규칙은 배포하지 않는다.
- 비밀번호 변경/재설정·세션 폐기 후 이전 비밀번호를 재사용해 로그인하는 검증은 하지 않는다. 새 승인된 테스트 로그인, 서버 관리 상태·검증 시각 등으로 결과를 기록한다. 작업 전 역할·반·GRAMMAR 권한은 보존하며 학습/시험 데이터는 수정하지 않는다.

Firebase의 비밀번호 재설정과 refresh token 폐기는 연관되지만, ID token 폐기 탐지에는 별도 확인 방식이 있다. [Firebase 공식 세션 관리](https://firebase.google.com/docs/auth/admin/manage-sessions).

## C. Git 이력·공개 복사본 대응 범위 — 실행하지 않음

1. 협업자·브랜치·태그·PR·포크·다른 clone과 중단 시간을 승인한다. 원본 ZIP과 제한된 감사 원본은 보존한다. 민감 Git bundle/대체 문자열 파일이 필요하면 공개 작업트리 밖에 두고 접근을 제한한다.
2. 실제 작업은 새 격리 clone에서 검토된 git-filter-repo로 준비한다. 공유 작업트리에 바로 실행하거나 복구 계획 없이 force push하지 않는다.
3. 과거 명단 `tools/students_import.csv`와 `backups/`는 전체 관련 이력에서 제거할 후보이다. 비밀번호가 들어갔던 소스·사용 설명·반 참고·템플릿은 필요한 기능을 보존하면서 민감 값만 대체한다. 이번에 분리한 정적 자료 `session.json`의 역사도 검토 대상이다. 단순 파일 삭제나 이름 변경만으로 끝내지 않는다.
4. 제한된 대체 규칙에서 원문을 메모리/비공개 파일로만 사용하고 명령줄 인수·로그·공개 patch에 옮기지 않는다. 정리 후 모든 관련 refs의 알려진 값 일치·필수 기능·개인 문서 제외를 검사하고, 승인된 refs만 갱신한다.
5. Git 이력 재작성은 커밋 ID를 바꾼다. `tools/public-release.json`의 기준 SHA도 안전한 대응 커밋으로 갱신하고 새 산출물을 재검토한다. 옛 SHA가 없다고 HEAD로 자동 대체해서는 안 된다.
6. 승인 후 협업자는 정리된 새 clone으로 전환한다. 기존 clone·태그를 다시 push해 민감 객체를 되살리지 않도록 조율한다. 공개 이력 정리와 별개로 자격증명 대응을 완료해야 한다.

GitHub의 SHA 직접 접근, PR 참조·캐시, 포크·이미 내려받은 clone은 force push만으로 제거되지 않을 수 있다. GitHub Support 지원 가능 범위는 민감 정보 여부와 자격증명 교체로 위험이 해소되는지에 따라 달라지며 제거를 보장할 수 없다. 소유자 연락·지원 요청 발송은 별도 승인 후 진행한다. [GitHub 공식 민감 정보 제거 안내](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## D. 캐시·산출물 검증 — 실행하지 않음

- Pages의 과거 파일 URL, raw GitHub/과거 SHA, 관련 PR·Actions artifact·다운로드 ZIP·포크를 범위별로 확인한다. 보호된 증거에는 URL·응답 상태·해시만 남긴다. 외부 삭제·지원 요청은 별도 승인한다.
- 현재 서비스 워커 소스는 network-only이며 새 CacheStorage를 만들지 않는다. 이것만으로 과거 브라우저 캐시까지 없다고 단정하지 않는다. 실제 기기의 해당 사이트 범위만 확인한다. origin 전체의 캐시·localStorage 삭제는 PDF LAB과 미전송 학습 기록에 영향을 줄 수 있어 자동 실행하지 않는다.
- Storage 다운로드 토큰 URL은 GitHub/Pages 캐시와 별개다. 규칙 배포만으로 폐기되지 않는다. 객체·사용처·호환 전달 계획을 별도로 확인하고 승인된 토큰만 폐기한다. 이번에는 객체/토큰을 조회·변경하지 않는다.

## 승인 항목을 분리한 완료 기준

| 묶음 | 별도 승인할 작업 | 완료 증거 |
|---|---|---|
| 공개본 | Pages Source 변경, 후보 활성화·push·배포 | 허용 파일만 배포, 민감 경로 404, 알려진 값 일치 0 |
| 계정 | 확정 UID별 자격증명·세션 조치, 필요 시 메일 | 원문 없는 UID별 비공개 결과·시각·실패/잔여 상태 |
| 이력 | refs별 정리·force push·협업자 전환 | 관련 refs 재검사·재클론 확인·잔존 복사본 목록 |
| 캐시 | artifact/캐시 정리·지원/소유자 요청 | URL별 재검증 및 삭제 불가/미확인 범위 |

공개본 정리만 끝난 상태를 사고 대응 전체 완료로 표시하지 않는다. 현재 단계는 G2 설정 완료와 G3 workflow 로컬 준비까지이며, 선별 커밋·push·수동 실행·환경 승인·배포는 아직 남아 있다.
