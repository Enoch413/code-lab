# P0 현행 상태 확인·대상별 조치안

조회일: 2026-10-21(KST). 로컬 기준 커밋: `75ab88069a9329a1e82fb69dbb4c35bd0c8262be`.

사용자가 **최신 운영 상태의 읽기 전용 확인까지만 허용**하여 G1을 수행했다. 실제 노출 제거·계정 변경·세션 폐기·설정 변경·Git 이력 재작성·push·배포·외부 메시지 전송은 하지 않았다. P0가 해결됐다는 결과가 아니다.

## 1. P0 공개 노출은 현재도 남아 있음

- 원격 main은 `db63b2b5dd221f22fe9569087b953583457b19ce`다. 로컬 보안 수정과 실행안 커밋은 아직 원격에 반영되지 않았다.
- 공개 GitHub main·과거 SHA·Pages의 명단 CSV가 모두 HTTP 200으로 응답했다. 세 응답은 기존 보존 명단과 같은 SHA-256이며 알려진 초기 비밀번호 값도 포함한다.
- Pages의 정적 PREP 자료도 HTTP 200이며 알려진 자료 비밀번호 값이 포함돼 있다.
- 본문은 메모리에서 비교한 뒤 보고서에 저장하지 않았다. 비밀번호·명단·토큰·실제 UID를 이 문서에 싣지 않는다. 과거 비밀번호로 로그인하거나 현재 유효성을 시험하지 않았다.

**최우선 조치안:** G2에서 자동 공개 경로와 환경 보호를 정비한 뒤, G3/G4에서 검토된 P0 산출물만 배포한다. 과거 Git 이력·캐시·외부 복사본 정리는 별도로 필요하다.

과거 명단 32행 중 현재 profile/Auth 일치는 총 31행이다. 일치한 계정에서는 Auth와 프로필의 비활성 여부가 일치했다. **이 수치는 기존 비밀번호의 유효성이나 실제 침해 여부를 입증하지 않는다.**

## 4. 공유 Firebase·Storage 상태

- Firestore와 Storage 운영 규칙은 이전 보존 관측과 같으며 로컬 강화 후보와 다르다. Firestore 규칙은 고정 P0 공개본의 기준 규칙과 일치한다. 긴급 공개본과 P1 권한 전환을 분리해야 하는 이유가 유지된다.
- 현재 단독 PREP 문서 1개는 새 권한 표식이 없고 단독 CHECK 문서는 0개다. 이번에는 지문·답안·상담 본문을 읽지 않았으므로 내용 기반 전환 후보는 확정하지 않았다.
- 전체 복합 인덱스 목록과 로컬 요구가 있는 5개 collection group을 각각 확인한 결과, 조회된 복합 인덱스는 0개다. 로컬 새 계약이 요구하는 인덱스 9개가 설치되지 않았다. 자동 단일 필드 인덱스가 없다는 뜻이나 기존 앱의 오류 9건을 뜻하지 않는다. P1 전환 전 별도 생성 승인·READY 확인이 필요하다.
- Auth 승인 도메인에 GitHub Pages 도메인이 포함돼 있다. 사용자 로그인은 시도하지 않았다.

Storage는 아래 4개 접두 범위의 객체 메타데이터만 조회했다. 전체 버킷·다른 버킷·모든 소비자를 조사했다고 주장하지 않는다.

토큰 값은 메모리에서 존재 여부/개수만 계산하고 폐기했으며 저장·출력하지 않았다. 객체 콘텐츠와 다운로드 URL은 받지 않았다. **영상 189개에 토큰이 있다는 사실만으로 그 URL 전부가 외부에 유출됐다고 단정하지 않는다.** G8은 공유 앱의 인증 전달·사용처를 확인한 뒤 대상 객체별로 승인해야 하며 일괄 폐기하지 않는다. 이미 받은 바이트는 회수할 수 없다.

## 5. 승인 순서와 현재 가능한 범위

1. **G1 완료:** 읽기 전용 현행 조회와 비공개 대상 목록 준비. 변경 직전에는 최신 상태를 다시 확인한다.
2. **P0 공개본 G2→G3→G4:** Pages 전환·환경 보호 → 선별 push/수동 workflow 활성화 → 승인된 P0 공개본 배포. 현 상태에서는 push하지 않는다.
3. **P0 계정 G5:** 현재 확인된 대상 중 관리자 복구 수단부터 확정하고 계정별 조치를 승인한다. 이력 정리나 P1 전체 완료를 기다릴 필요는 없다.
4. **G6/G7:** 새 격리 clone의 이력 정리·승인 refs 갱신·캐시/artifact 정리. 모두 미실행이다. 고정 P0 SHA의 대응값 재검토 없이 이력을 바꾸지 않는다.
5. **G8 및 P1:** 토큰별 조치와 자료·인덱스·규칙·두 앱 전환은 호환성·중단/복구 계획을 별도 승인한다.

로컬에서는 상태 대조와 제안 문서만 갱신했다. 운영 변경 승인은 아직 없으므로 실제 P0 수정 완료를 선언하지 않는다.

## 조회 방식과 제한

GitHub는 GET만 사용했다. Firebase는 규칙/인덱스/승인 도메인/객체 메타데이터 GET, 필드 제한 Firestore 조회, 관리자 Auth UID 조회만 수행했다. 관리자 API용 access token을 받았지만 사용자 로그인·자격증명 변경·사용자 세션 갱신은 하지 않았다.

Auth의 `accounts:lookup`은 HTTP POST를 사용하는 읽기 API이며 공식 문서도 관리자 조회로 정의한다. [Auth 계정 조회](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/lookup), [복합 인덱스 목록](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.collectionGroups.indexes/list), [Storage 객체 목록](https://docs.cloud.google.com/storage/docs/json_api/v1/objects/list).

초기 인덱스 조회 한 번은 HTTP 400이었고, 요청을 단순화한 뒤 전체/개별 group 조회가 성공했다. branch protection 404는 유효 branch rules 조회와 구분해 기록했다. 실패한 요청을 성공 증거로 사용하지 않는다.

정확한 UID/객체 이름·메타데이터·refs·읽기 요청 감사 기록은 접근 제한 `.local`에만 보관한다. 외부 캐시·삭제 객체·모든 다운로드본, 실제 비밀번호 유효성·침해 여부·사용자 로그인·운영 쓰기·실기기·원격 CI는 미확인이다. [P0 실행안](P0_EXECUTION_PLAN.md)의 승인·중단·복구 조건을 계속 적용한다.
