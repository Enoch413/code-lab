# 로컬 운영 준비·전환·영상 검증 결과

검증일: 2026-10-21. CODE LAB `a7cc5b3`, PDF LAB `da3a6e3` 기준이다. 운영 Firebase와 GitHub에 접근하거나 데이터를 변경하지 않았으며 커밋·push·배포·메시지 전송은 하지 않았다. 공개 가능한 결과만 이 문서에 기록한다. 원본·UID별 대응표·입력/전환 계획·상세 로그는 Git에서 제외된 접근 제한 폴더에 보관한다.

## 1. P0 실행안

[P0 실행안](P0_EXECUTION_PLAN.md)에 긴급 공개본, 계정/세션, 이력/캐시, 다운로드 토큰의 승인 단위·순서·중단·복구 기준을 정리했다. 공개본 후보는 최신 P1과 분리한 기존 고정 P0 SHA를 유지했다.

공개 파일 21개 응답/해시와 민감 경로 16개의 로컬 404, 기존 공개본 검사 39개·CSV 검사 17개를 통과했다. 알려진 비밀번호 및 명단 개인 이름의 공개본 일치는 0건이다. 일반 관리자 역할명과 명단 표시명의 일치 1행은 역할·권한 안내 소스를 확인한 뒤 구분했으며 실제 개인 이름을 허용한 예외가 아니다.

과거 명단 32행 중 31행은 당시 profile loginId/문서 ID/Auth UID가 단일 일치했고 1행은 추가 확인이 필요하다. 그중 관리자 프로필은 3개다. **현재 계정으로 확정한 수는 0이며, 운영 계정 변경 목록으로 승인된 상태가 아니다.**

## 2. 보유한 과거 자료의 진단

2026-10-15 보존 백업에서 필요한 컬렉션만 읽어 오프라인 입력을 만들었다. Auth/Storage 전체 목록은 변환 입력에서 제외했다. profile/자료 자체에도 개인정보나 과거 다운로드 URL이 있을 수 있어 입력과 전체 산출물을 비공개로 보관한다. 실제 백업의 쓰기 후보는 만들지 않았다.

| 대상 | 과거 문서 수 | 이번 처리 |
|---|---:|---|
| 사용자 프로필 | 75 | 과거 UID 대조 참고. 현재 운영 사용자 수로 해석하지 않음 |
| PREP 자료 | 153 | 기존 권한 계약 검토 필요 |
| CHECK 자료 | 109 | 기존 권한 계약·배정 방식 검토 필요 |
| 상담 슬롯 | 1 | 검증기가 잡는 비공개 추가 필드 없음 |
| CHECK 응답 | 72 | 이 백업에서는 비표준 ID 없음 |
| 집계 자료 | 4 | 내용 검토 및 필요한 분리 작업 대상 |

프로필을 제외한 inventory 339개 중 미해결로 표시된 것은 266개다. PREP/CHECK 262개와 집계 4개이며, 검증 오류 종류는 같은 문서에서 중복될 수 있다. 이 수는 새 코드 버그 266건이나 현재 운영 자료 266개를 뜻하지 않는다.

오프라인 검증기에 빈 replacements를 전달해 inventory만 생성했다. **실제 백업에 대한 승인 후보 쓰기 0건, 삭제 0건, 에뮬레이터 적용 0건**이다. 단순 표식 추가·이름 기반 UID 추정·일괄 복원은 하지 않았다. 최신 운영 사본과 내용 확인 없이 과거 자료를 승격하지 않는다.

## 3. 합성 자료의 실제 SDK 전환·복구 리허설

운영용 실행 도구를 새로 만들지 않고, 기존 양 앱 브라우저 검사에 무시 폴더 안의 합성 리허설을 추가했다. 고정 loopback Auth/Firestore/Storage 에뮬레이터와 demo 프로젝트만 사용했다. 실제 앱과 Firebase SDK·현행 로컬 규칙으로 아래 6개 시나리오를 통과했다.

1. 원본이 계획 이후 바뀌면 transaction이 중단되고 새 대상이 생성되지 않는다.
2. transaction 내부의 의도적 실패는 부분 쓰기를 남기지 않는다.
3. 전체 관리자의 승인 형태 후보는 학생이 읽을 수 있는 자료가 되며 원본은 그대로 남는다. 이미 존재하는 대상에는 같은 복사를 재적용하지 않는다.
4. 새 대상의 복구 삭제는 대상이 바뀌었으면 거부하고, 변경되지 않은 합성 복사본만 삭제한다. 원본은 보존한다.
5. 상담 슬롯의 비공개 필드 제거는 예약·소유권을 유지한다. 정리 후 비공개 필드를 다시 넣는 시도는 규칙이 거부한다.
6. CHECK 응답의 표준 ID 복사는 답안과 원본을 보존하며 새 복사본을 되돌려도 원본이 유지된다.

**복구 계획의 제한:** 슬롯 원본의 비공개 필드를 공개 점유 문서로 다시 복사하는 복구를 하면 안 된다. 원본은 비공개 증거로 유지하고, 허용된 예약/상태 필드만 복구하거나 별도로 검토한 비공개 저장 방식을 사용한다. 새 대상 삭제도 운영에서는 개별 승인이 필요하다. 응답 복사 후 구형 문서를 그대로 둔 상태는 중복 집계 위험이 있으므로 실제 전환에서는 검증 후 정리 순서를 따로 승인해야 한다.

기존 PDF 배정 → CODE 학생 제출·권한 거부 후 재시도 → PDF 응답 반영·2차 오답 생성 → 소유자 저장/재조회, PREP 영상 변경·두 삭제 경로를 포함한 브라우저 통합 8묶음도 같은 최종 실행에서 통과했다.

## 4. 실제 디코딩 가능한 영상과 제한된 네트워크

로컬 FFmpeg로 개인정보 없는 H.264 무음 MP4 3개를 생성했다. 운영 영상·Storage 객체를 다운로드하지 않았다. 실제 인증 다운로드 helper와 PREP 영상 렌더러에서 아래를 확인했다.

| 파일 크기 / 영상 | 화면 너비 | 결과 |
|---|---|---|
| 863,171 bytes / 4초·640×360 | 390·1280 CSS px | 실제 첫 프레임, 3초 탐색, Blob 해제 통과 |
| 24,491,090 bytes / 24초·1280×720 | 390 CSS px | 실제 첫 프레임, 23초 탐색, Blob 해제 통과 |
| 119,716,084 bytes / 60초·1920×1080 | 390 CSS px | 실제 첫 프레임, 59초 탐색, Blob 해제 통과 |

Windows의 headless Edge에서 총 4개 재생 케이스를 통과했다. 작은 화면 너비는 실제 휴대폰을 뜻하지 않는다. 약 119.7MB 파일의 로컬 첫 프레임은 약 0.3초였지만 loopback 환경의 관측치이므로 인터넷 성능이나 휴대폰 성능으로 일반화하지 않는다.

별도로 다운로드 2MiB/s·지연 80ms 조건을 걸고 약 24.5MB 파일의 로딩 표시, 중간 취소 후 소스 미부착, 다시 불러오기, 메타데이터 확인, 소스 해제를 통과했다. 다시 불러오기에는 약 12.2초가 걸렸다. **현재 플레이어가 전체 파일 다운로드를 기다리는 동작은 유지된다.**

### 중간 실패와 최종 성공의 구분

초기 검사에서는 Playwright `route.fetch`/`route.fulfill`로 응답 전체를 중계할 때 큰 파일 다운로드 중 page/context 종료가 두 번 재현됐다. HTTP/HTTPS 프로토콜을 바꾸는 `route.continue` 시도는 Playwright 제한으로 거부됐다. 이 시도들은 통과로 계산하지 않는다.

최종 검사에서는 테스트 페이지의 demo Storage fetch만 고정 loopback 에뮬레이터로 매핑해 브라우저가 직접 받게 했다. 그 상태에서 기존 8묶음·합성 전환 6개·영상 4개와 제한 네트워크 검사를 통과했다. 앱 소스를 바꾸지 않았다. 중계 경로를 피했을 때 성공한 증거이며, 중계 실패의 정확한 내부 원인이나 메모리 한계를 규명했다고 주장하지 않는다.

Android/iOS 실기기, 수업에 쓰는 다른 코덱·오디오, 최대 500MB 파일, 저메모리 환경, 프로세스 전체 메모리량은 미검증이다. 스트리밍·부분 다운로드 구현을 추가하지 않았다. 이 항목들은 운영 전 검증 조건으로 남긴다.

## 5. 결과와 별도 승인 항목

- 로컬 완료: P0 실행안 확정, 고정 공개본 재검증, 과거 사본의 진단/개인별 대조 후보 정리, 합성 자료 전환·복구와 실제 코덱 재생·취소/다시 불러오기 검증.
- 소스 변경: 새 문서 2개뿐이다. 앱·규칙·의존성·workflow는 수정하지 않았다. 검사 도구와 비공개 산출물은 Git 후보에서 제외했다.
- 먼저 승인할 수 있는 다음 단계: [P0 실행안](P0_EXECUTION_PLAN.md)의 G1 읽기 전용 현행 상태 확인. 공개본 조치를 위한 G2 이후, 계정 변경 G5, 이력/캐시 G6/G7, 토큰 폐기 G8은 각각 별도 승인한다.
- 별도 운영 전환: 최신 export·UID·반/개인 배정·인덱스·양 앱 호환 확인, 승인 후보별 모의 검증과 source/target 사전조건 재확인, 조율된 자료/규칙/앱 반영. 과거 백업으로 운영을 덮어쓰지 않는다.
- 원격 CI·푸시·배포와 실제 계정 로그인/생성/저장/삭제는 미실행이다. main push는 Pages 배포를 유발할 수 있으므로 로컬 준비 완료와 구분한다.

공개 노출 제거·계정 보호·운영 호환성 완료를 선언한 결과가 아니다. 로컬 증거로 닫을 수 없는 항목은 승인 전 미완료 상태로 유지한다.
