## 3. 계정 조치 계약

1. 현재 Auth UID를 기준으로 대조하고 과거 계정의 존재·역할·반·비활성 상태를 재확인한다. 로컬에서 단일 일치했던 31행도 재확인이 필요하다. 미일치 1행은 추정으로 실행하지 않는다.
2. 관리자 접근을 잃지 않도록 복구 경로를 먼저 검증한다. 노출이 확인된 계정에만 개별 비밀번호 변경/재설정과 세션 대응을 적용한다. 전체 계정 삭제·재생성, 공통 새 비밀번호, 과거 비밀번호로 로그인 시험을 하지 않는다.
3. 새 비밀번호·재설정 링크·토큰은 터미널·Git·CSV·보고서에 남기지 않는다. 메일이나 다른 전달은 대상·방법에 대한 명시적 승인을 받은 뒤에만 수행한다.
4. 세션 폐기 후에도 이미 발급된 토큰과 내려받은 데이터의 잔여 접근 가능성을 따로 검증한다. 즉시 차단이 필요하면 해당 계정의 비활성화 범위와 공유 서비스 영향을 추가 승인한다.
5. 계정 작업이 실패하면 다음 대상 처리를 중단하고 비공개 결과만 보존한다. 옛 비밀번호를 복구하거나 학습/시험 데이터를 초기화하지 않는다.

## 4. 중단·복구 기준

- 현행 Pages 설정·규칙·배포 소스가 기존 증거와 다르면 작업을 중단하고 계획을 재검토한다. 현행 운영 상태를 로컬 기록과 같다고 가정하지 않는다.
- 공개본 검사에서 민감 값, 허용 목록 밖 파일, 누락 자산, 비어 있지 않은 정적 자료가 발견되면 배포하지 않는다.
- 공개본 장애 시 민감 정보가 있던 저장소 루트나 과거 전체 배포로 되돌리지 않는다. 검증한 안전한 산출물 또는 승인된 정비 화면만 사용한다.
- 이력 재작성으로 고정 source SHA가 바뀌면 대응하는 안전한 SHA를 다시 검토해 명시적으로 갱신한다. 빌드가 실패했다고 HEAD로 자동 대체하지 않는다.
- 사이트 origin 전체의 CacheStorage/localStorage 삭제는 하지 않는다. 공유 PDF LAB 상태·미전송 기록을 먼저 확인하고 대상 범위별로 승인한다.
- D 드라이브 원본 ZIP·보호 원본·기존 감사 증거는 보존한다. 사고 대응 완료를 위해 원본 증거를 삭제하지 않는다.
